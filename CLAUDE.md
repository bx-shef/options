# Памятка агенту: shef.options

Библиотечный модуль Битрикс24 «коробки». Штатное поведение платформы не
меняет — даёт другим модулям слой опций, enum-ы ядра, трейты, абстракции и
интерфейсы. Ставится как обычный локальный модуль; остальные модули линейки
рассчитывают, что он уже стоит.

Проверок перед сдачей две, и обе гоняет CI: `./build.sh --check` — состав
поставки, синтаксис, тесты; `composer run lint` — форматирование
(php-cs-fixer, набор `@PSR12`). Линтер стоит в `require-dev` и из `build.sh`
не зовётся намеренно: сборка обязана отрабатывать в свежем клоне, где
`composer install` ещё не запускали.

**Как работа попадает в `main`** — [docs/agent-rules.md](docs/agent-rules.md):
только через PR; `/code-review` на каждый PR, а на изменения поведения,
безопасности, данных клиента, установщика и CI — панель из пяти проверяющих
(документация, инженер, QA, безопасность, CTO); чек-лист перед мержем и после;
рабочая дисциплина (замер вместо «должно», тест краснеет при поломке, никогда
`git checkout --`) и то, что необратимо и решается владельцем.

## Приёмочный чек-лист

Всё, что ниже рантайма Битрикса, тестами не покрыть: установка, права, кеш,
раскладка файлов, поведение при обновлении. Процедура целиком — в
[docs/portal-check.md](docs/portal-check.md): десять шагов с ожидаемым
результатом, что делать, если не сошлось, и бланк результата.

Два правила, которые важнее самого списка:

* **проходить перед сдачей, а не после жалобы.** Забытый шаг находит не
  разработчик, а клиент;
* **на отдельном стенде.** Шаги с удалением модуля и с порталом в CP1251 на
  рабочем портале делать нельзя.

Главный сценарий для 3.0.0 — обновление со стенда с 2.x: там проверяется, что
вкладки «Документация» больше нет, сохранённые настройки на месте, а
`/bitrix/js/shef-options` уходит при деинсталляции.

## Документация и практики Битрикс

### Источники
Документацию Битрикс берём из локальных клонов официальных репозиториев, а не из памяти модели и не со сторонних сайтов:

- `.bitrix-docs/framework-docs/` — Bitrix Framework (D7, ORM, модули, компоненты, контроллеры, события ядра). Исходник: https://github.com/bitrix-tools/framework-docs
- `.bitrix-docs/b24-rest-docs/` — REST API Битрикс24 (методы, события, вебхуки, приложения). Исходник: https://github.com/bitrix-tools/b24-rest-docs

Скиллы с правилами написания кода: https://github.com/bitrix-tools/best-practice
- `bitrix-best-practice-core` — контроллеры, роутинг, конфигурация, базовые сущности
- `bitrix-best-practice-sql` — работа с БД и ORM

### Первичная настройка (если папки `.bitrix-docs/` нет)
1. Склонировать документацию:
   ```bash
   mkdir -p .bitrix-docs
   git clone --depth 1 https://github.com/bitrix-tools/framework-docs.git .bitrix-docs/framework-docs
   git clone --depth 1 https://github.com/bitrix-tools/b24-rest-docs.git .bitrix-docs/b24-rest-docs
   ```
   Общий клон линейки уже лежит уровнем выше — `../.bitrix-docs/` (каталог `tools-ai`); можно пользоваться им.
2. `.bitrix-docs/` — в `.gitignore` проекта (уже добавлено).
3. Установить скиллы:
   ```bash
   npx skills add bitrix-tools/best-practice --skill bitrix-best-practice-core
   npx skills add bitrix-tools/best-practice --skill bitrix-best-practice-sql
   ```

### Правила работы
- Перед тем как писать код с API Битрикса, найди нужную статью поиском (grep/rg) по соответствующему клону и опирайся на неё. Не выдумывай классы, методы, параметры и поля.
- Задачи по D7, ORM, модулям и компонентам решай по `framework-docs` вместе с исходниками ядра проекта в `/bitrix/modules/`. Если документация и код ядра расходятся, прав код ядра (он соответствует установленной версии). Расхождение отметь в ответе.
- Задачи по REST-методам, событиям и приложениям Битрикс24 решай по `b24-rest-docs`. Если подключён MCP `b24-dev-mcp`, им тоже можно пользоваться.
- Для решений «как правильно писать» (структура, контроллеры, запросы к БД, ORM) применяй скиллы `bitrix-best-practice-core` и `bitrix-best-practice-sql`.
- Не используй устаревшие API (старое ядро `C*`-классов), если в D7 есть замена. Исключение: проект явно требует старое API.
- В ответе указывай путь к файлу документации, на который опирался.
- Обновление коробки из консоли — `php bitrix.php update:modules` (`framework-docs/pages/framework/console-commands.md`).

## Разовые контейнеры проверок

- Любые разовые `docker run` для проверок (Playwright, node, php…) — только через `../stand/tools/pw-run.sh <проект> <задача> [опции docker run] -- <команда>` (bx-shef/toolsai-stand, клон рядом). Образ Playwright — по умолчанию, другой — `PW_IMAGE=node:22`. Прямой `docker run` для проверок не использовать: обёртка задаёт лимиты памяти и CPU, shm 1 ГБ, --init, отключает дампы WSL, даёт имя, метку project и таймаут (PW_TIMEOUT). Не больше двух прогонов одновременно. Пример: `PW_TIMEOUT=900 ../stand/tools/pw-run.sh <репо> check -v D:/tmp/chk:/w -w /w -- bash -c './build.sh --check'`.
